## Exit criteria

Testing passes when both of these are true:

- Every requirement and constraint below has been checked.
- No critical or high severity bugs are open. Medium and low severity bugs may ship if the release notes list them.

| Severity | Meaning                                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| Critical | Exposes data or credentials, changes Claude Code files or sessions without the user's request, or loses data |
| High     | A requirement fails, or the dashboard gives a wrong answer with no warning                                   |
| Medium   | A requirement works with a noticeable problem, and a workaround exists                                       |
| Low      | Cosmetic, or unlikely to affect use                                                                          |

### M2 script

1. Start NVDA, then start the tool and open its page in your browser.
2. Press `Insert+Down Arrow` to read the page from the top. Check that groups, counts, names, and reasons make sense.
3. Press `Insert+F7` and choose Headings. Check that each group is listed.
4. Press `Tab` to reach the Stale section and press `Enter`. Check that its expanded state is announced. If no Stale section is shown, record this step as not run.
5. With the page open, make a session hit a permission prompt. Check that NVDA says the session needs you, with its reason, without you moving focus.

## Performance

One `claude agents --json --all` run used about 353 ms of CPU, averaged over 12 runs on an 8-core Windows PC on 2026-11-06. This excludes the shell wrapper and transcript reads. At the 3-second interval, that is about 10.5% of one core, or about 1.3% of the whole PC.

On the first live run, across 6 measured changes, the slowest upper bound was 2309 ms. On the re-run, the slowest upper bound was 3686 ms. On the first run, across 94 polls, the poll cycle had a median of 3392 ms and a maximum of 3531 ms. On the final code, across 14 changes under normal polling, upper bounds were 3801 to 3946 ms, and the poll cycle had a median of 3368 ms and a maximum of 3507 ms. The strict worst case is about 4.1 seconds: run, interval, run, and delivery. FR-9 is at risk once one run takes more than about 950 ms. This wasn't measured under heavy load.

### Security review

The NFR-9 review, by an independent agent on `2a0dba7`, found one High issue and two Lows. The owner chose to fix the High before release.

- **H-1, fixed in #29:** browsers send a cookie to every port on a host, so another local program could get the session cookie and run actions. A per-port page key now guards actions and the WebSocket. All 32 proof checks passed: every request with the stolen cookie and forged headers but no valid key was refused, and the controls with the key succeeded.
- **L-1, fixed in #29:** Stop and Delete didn't check the short ID's format before passing it to `claude`.
- **L-2, fixed in #29:** a second start could trust whatever answered on a stale lock's port. Both sides now prove they know the secret without sending it.
- **Info, accepted:** Ctrl+Break also reaches the session's parent shells; checking a UNC folder makes an SMB connection; Resume loads the folder's own settings; and Chrome may record the sign-in redirect, with the page key, in its history.

### Security review

The NFR-9 review, by an independent agent on `b2d3348`, found no Critical or High issue.

- **L-1, fixed in #47:** the helper's `check` didn't confirm that a recorded wrapper's entry in its process snapshot was the same process. If the wrapper exited and its ID was reused, a child of the new process could have joined the offer. Very unlikely, and each entry was still checked by handle before ending.
- **Info, accepted:** the 1 MB input limit is checked after reading; the tool's own processes are worked out on each run rather than at startup, and the design now says so; a recorded process ID reused by an elevated process or one run by another user can keep an offer showing until a restart; daylight saving could make start times disagree by an hour, which only causes a refusal; the handover link's 60 seconds use the wall clock; model, speed, and routing strings from transcripts have no length cap; and a first sign-in link handed to a browser that opened never expires until it's used, and is briefly on `rundll32`'s command line, where other processes of the same user can read it. Iteration 2's accepted items still apply.
